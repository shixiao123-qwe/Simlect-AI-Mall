# 售后审核、退货验货与退款履约

2026-11-02 源码核对：工作区无Git，不覆盖用户修改。复用Common管理员拦截器、AdminSensitiveConfirm一次性二次确认、OrderInfoServiceImpl.refund的实付分摊/稳定退款锚点/事务提交后库存回补。

实施计划：增加after_sale_fulfillment扩展表，不改原申请状态检查约束；APPROVED下用phase表达待退货/待验货/可退款/退款失败，完成后主状态COMPLETED。审核、验货、退款为管理员明确操作，AI只读进度；用户只提交本人退货单号。退款复用Java原业务并扩展受审核后的已完成订单退款入口，旧直接退款接口状态规则不变。验货区分接受退货和是否可重新入库。

只通过本地模拟渠道验证，无真实资金操作。新增管理端页面及用户申请进度页面，接入已有路由和确认票据。已有真实申请不自动批准、不自动退款。换货需要出库/重新发货，当前明确不支持批准换货，不伪造履约成功。

验收覆盖状态跳转、权限、敏感票据、重复操作、已完成订单的受控退款、不可售退货不补库存、支付失败重试与审计、真实MySQL事务回滚、前端编译和回归。实际结果在执行后追加。


## 最终实现与状态

主申请状态保持原有 PENDING_REVIEW / APPROVED / REJECTED / COMPLETED，避免破坏原活跃申请唯一索引。履约阶段放在新表 after_sale_fulfillment：

```text
用户确认提交 -> PENDING_REVIEW
管理员驳回 -> REJECTED
管理员批准退款 -> APPROVED / READY_REFUND
管理员批准退货退款 -> APPROVED / WAIT_RETURN
用户提交本人退货单号 -> WAIT_INSPECTION
管理员验货拒绝 -> REJECTED
管理员验货接受 -> READY_REFUND（同时记录是否允许重新入库）
管理员二次确认退款 -> REFUNDING -> COMPLETED
                           -> REFUND_FAILED（需人工核实后重试）
```

REFUNDING 在资金执行事务中使用，成功时与其审计一起提交；外部调用失败则回滚该事务，再单独记录 REFUND_FAILED。失败表示“未完成/待核实”，不能据此断言渠道从未发生资金动作。审批不执行退款，填运单不等于物流商验真，验货接受不等于商品可重新销售。

### 退款与库存的真实链路

`AfterSaleAdminController.refund` -> 管理员会话 + AdminSensitiveConfirm一次性票据 -> `AfterSaleWorkflowService.refund` -> 支付生命周期Redis锁 -> 持久化/恢复原退款单号 -> 数据库事务 -> Order/Item/Application锁及状态检查 -> `OrderInfoService.refundAfterSale` -> 原 `refundInLock/doRefund` -> 原实付金额/优惠分摊 -> 原 PayFeignSupport.refund -> 本地模拟或已配置支付渠道 -> 订单及订单项退款状态 -> 验证真实退款金额/单号 -> 全部子订单都退款时 PayFeignSupport.markRefunded -> 售后COMPLETED与审计。

退款不是模型生成金额。管理员接口也只收申请编号，不能提交任意金额、用户ID、退款单号或状态。普通用户不能访问管理端审核/退款接口，AI新工具只读进度，不具备批准或执行退款工具。

原直接退款入口仍只允许原有订单状态；为已完成订单的已审核退货，新增独立 AFTER_SALE_FULL_REFUND / AFTER_SALE_PARTIAL_REFUND 状态机事件及受信任Java方法，不放宽旧用户接口。原订单与库存主流程没有重写。

未发货退款按原幂等操作ID回补库存；退货退款必须经过验货，restockable=false时不回补可售库存。损坏品需要人工仓库隔离，当前没有独立WMS隔离库位系统。可售品仍走原事务提交后库存回补及远程补偿记录；库存服务临时失败时，资金/申请完成不代表库存回补已经同步完成，应查原补偿任务。

部分退款的订单状态7不能证明未发货：新增读取真实物流状态，禁止用部分退款状态绕过退货验货。订单已发货时，退款类型申请不能直接执行，需重新核实退货退款流程。

### 幂等、失败和审计

- 数据库保留原同明细活跃申请唯一约束；审核和阶段变化有锁与旧状态条件更新。
- 提交、审核、寄回、验货、执行、失败、完成都有after_sale_log，actor由后端登录态提供，不接受客户端伪造。
- 审核/验货/退款复用管理员密码换取的短期一次性确认票据，绑定管理员及目标操作路径。不能拿审核票据执行退款，重放票据失败。
- 执行退款前先在独立事务里持久化原退款单号，兼容原Redis锚点；Redis丢失/到期后可从SQL恢复，同一申请重试仍用原单号。发现持久化与Redis单号冲突就拒绝执行。
- 回调结果与持久化退款单号、订单项已退款状态和实际退款金额一致，才允许标为完成。重复完成请求不再调用资金接口。
- 一旦退款单号已绑定或处于待核实状态，不能再驳回释放申请，避免结果不明时通过新申请再次退款。
- 所有子订单均已退款，才把整笔支付记录标为REFUNDED；支付记录没有部分退款状态，因此部分退款明细以订单项和售后记录为准。
- SQL与外部支付服务不是同一个原子事务。远程成功但本地提交/支付记录更新失败时，可能暂时不一致，需按原单号核实重试；不宣称跨系统绝对exactly-once。

## 页面与接口

管理员页面：`http://127.0.0.1:6002/admin/order/afterSale`，登录后“订单 → 售后审核”。移动端对应 `/admin/m/order/afterSale`。用户页面：`http://127.0.0.1:6001/after-sale-requests`，原“售后管理”页面也增加入口。AI可问“我的售后进度”。旧绿色确认卡是申请提交时的回执，不会自动变成实时履约状态，最新状态看进度页或AI查询。

| 接口（Gateway外部路径） | 用途 |
|---|---|
| POST /admin-api/order/afterSale/list、detail | 管理员分页列表/详情/审计 |
| POST /admin-api/order/afterSale/review | 批准或驳回；需一次性确认票据 |

管理员身份既有全局拦截器也有新Controller显式会话检查，避免错误关闭拦截器后暴露新接口。资金入口默认 `SIMLECT_AFTER_SALE_REFUND_ENABLED=false`；本机演示显式开启。当前 `SIMLECT_PAY_LOCAL_MOCK_ENABLED=true`，执行的是完整业务状态的模拟资金退款，不会发生真实资金退回。真实渠道需正确证书和密钥，本次未修改、未调用、未验证真实资金渠道。

退货地址来自服务端配置 AFTER_SALE_RETURN_ADDRESS；空地址不能批准退货退款。本机配置明确标注“本地演示仓库（仅测试，请勿寄送真实包裹）”，不可按这个地址真实寄件。物流单号只是人工登记，不接第三方轨迹验真。

## 用当前申请进行网页验收

1. 当前申请仍为待审核，未替用户审批或退款。打开管理端并登录，找到当前申请，点批准，填写审核原因并输入管理员密码换取一次性票据。
2. 当前类型是refund且订单未发货时，进入可执行退款阶段。用户刷新进度页或问AI，应看到“待管理员执行退款”。
3. 管理端点“执行模拟退款”，再次确认管理员密码。应看到申请完成、实际退款金额/退款单号；用户进度页明确“本地模拟退款完成，未发生真实资金退回”。订单及订单项应变为已退款，单SKU回补按原幂等库存流程完成。
4. 再点执行不能二次退款；已退款明细再次发起售后应被拒绝。
5. 测试退货退款时，需要另一笔已发货或已完成演示订单；当前refund申请不能伪装成退货验货。批准return_refund -> 用户填写测试物流DEMO123456 -> 管理端验货 -> 明确损坏品不勾可售 -> 执行模拟退款 -> 验证库存没有回补。
6. 驳回分支另用一笔申请；换货类型会明确拒绝批准，因为换货出库未接入。

管理员账号/密码沿用 `deploy/.env.local` 的ADMIN_ACCOUNT/ADMIN_PASSWORD，不新增或打印凭证。未来整套启动要包含管理前端，可从项目根目录运行 `start-local.cmd`（不加-WebOnly）；停止仍用stop-local.cmd。

## 源码理解与面试讲法

为什么增加扩展表：原申请表和唯一索引已运行，轻量方案保留主状态，将退货、验货和执行细节放扩展表，老申请首次审核时懒初始化，不要求清库重建。

为什么审批与退款分离：批准是管理决策，退款是不可忽略的资金副作用；退货还需要人工收货和可售性判断。模型不能代替管理员验货，也不能靠一句“退款成功”改变资金事实。

为什么需要Redis锁和SQL条件更新：锁串行支付/关单/退款，SQL条件更新抵御状态变化与重复请求，数据库和稳定渠道单号负责最终幂等；它们各自覆盖不同失败窗口。

为什么退款单号要先持久化：只依赖Redis TTL，远程可能已退款但本地回滚后很久再试，可能生成新单号。SQL保存原号并恢复Redis，使重试走同一渠道请求编号。

为什么不能把全部退货加库存：验货接受表示同意退款，不代表可再次销售；损坏品不能进入可售库存。本项目只记录人工隔离意图，实际WMS隔离数量和库位不是本次范围。

为什么保持旧退款权限：原用户退款状态有明确边界；只有经过审核验货的新Java路径使用新增状态机事件支持已完成订单，不把原直接接口权限全局放宽。

诚实边界：这是Java/MCP/人工审核协同的售后退款闭环。本地资金模式、模拟物流单号、人工验货，不是全自动退款、物流验真或换货发货系统。真实渠道、压力、故障恢复和第三方仓库对账仍需额外验收。
