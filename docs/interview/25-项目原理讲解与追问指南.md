## 二、如何学习，才能经得住追问？

### 1. 不先背答案，先追踪一个用户动作

从“搜索蓝牙耳机”或“提交订单”开始，只打开这一条链上的文件。每看到一个调用，都在纸上写：输入是谁给的、输出是什么、它是否会写数据、失败后谁收尾。读完后合上文件，用自己的话讲一遍，再回源码核对。

第一遍不要陷入实体类的所有 getter。先知道对象代表什么事实，再追它在哪里被赋值和检查。比如 `requestId`、`traceId`、`actionToken` 都像随机串，职责却完全不同；如果不能解释差别，继续背框架没有帮助。

### 2. 每个答案练成三种长度

- **30 秒：说明问题和方案。** 例如“推荐价格不能信模型，所以由 Java 重新检查 SKU”。
- **90 秒：说出执行顺序和源码。** 用户需求 → ShoppingPatch → 会话合并 → MCP 召回 → Java 批量筛选 → 核验结果 → 展示。
- **3 分钟：加入故障和取舍。** 库存变化怎么办，Java 超时怎么办，旧卡片如何避免误用，为什么没有给模型数据库写权限，当前评测证明到哪里。

面试官追问通常是在要求你从第一层进入第二层、第三层。如果只反复说“防幻觉、保证一致性”，没有具体条件和结果，就是没有进入源码层。

### 3. 用统一答题顺序组织语言

建议按“业务问题 → 当前实现 → 一次执行 → 异常分支 → 验证证据 → 代价与边界”回答。不是每道题都逐项背标题，而是让答案具备这些信息。

例如问为什么引入确认卡：先说售后是写操作，文字理解可能有歧义；再说提案先保存服务端参数，用户确认后读取原参数执行；接着讲归属校验、锁、CAS 和 Java 幂等；最后解释响应丢失不能直接重提。这样一题能自然接到权限、状态机、幂等和分布式故障。

### 4. 把基础八股放回具体代码

概念补读使用 [技术栈原理与源码详解](23-项目技术栈原理与源码详解.md)、[Java 后端面试问题](05-Java后端面试问题.md) 和 [AI 应用开发面试问题](06-AI应用开发面试问题.md)。优先掌握下面这些对应关系：

| 基础知识 | 本项目中的落点 | 要练习的深入问题 |
| --- | --- | --- |

## 三、先把三个最重要的原理讲透

### 原理一：结构正确，不等于事实正确

模型返回 `{"max_price":300}`，Pydantic 可以检查价格字段合法、没有额外字段，但不能证明某个 SKU 现在售价 199、库存 10。检索也可能返回过期索引。所以模型负责表达需求，ES 负责候选，Java 负责核验业务事实；下单仍需重新检查。

可以类比为：模型填写采购需求单，搜索找备选，业务系统核对库存和报价。需求单填写规范，不代表仓库真的有货。

追问方向：否定条件如何解析？软偏好如何排序？模型返回非法字段怎么办？多轮修改怎样保留其他条件？上一轮第一款在下一轮还能指什么？答案都在第三讲。

### 原理二：一次业务动作，会跨越多个成功层次

浏览器请求被接收、MCP 调用完成、Java 事务提交、售后审核通过、模拟退款完成，不是同一件事。尤其网络超时只代表调用方没有及时拿到确定结果，远程可能已经提交。

所以要分别保存执行中的状态、业务事实与恢复线索。售后确认有数字状态，申请有 SQL 总状态，退货退款有履约 phase；不能拿一个“成功”字段贯穿全部。

追问方向：Java 成功而 Redis 回写失败怎么办？锁到期能不能重做？按原 requestId 查不到是否立刻再提交？为什么需要 recover_only？答案在第四讲。

### 原理三：本地事务、锁、幂等和消息分别承担不同责任

本地事务让同一数据源的一组写入共同提交或回滚；行锁协调数据库并发；幂等标识防止同一业务操作重复产生效果；Outbox 保存待发送意图；Inbox 协调本地消费完成；补偿处理跨服务已经发生的副作用。它们是组合关系，不是某一个技术包办全部一致性。

本地 Seata 关闭时，Order 的数据库回滚不会自动撤销 Stock 已提交的扣减。Redis owner 锁也有租约，不能替代 MySQL 持久幂等。ACK 代表消费方对消息的确认，不是所有远程操作永远成功。

追问方向：预检查锁何时释放？最后一件商品怎样防超卖？扣减响应丢失怎么办？补偿比扣减先到呢？消息已经发布但状态没更新呢？第二讲逐步推演。

## 四、3 分钟项目介绍参考稿

下面是表达结构参考，不要求逐字背诵。个人贡献范围应按实际做过、能解释的文件调整；继承的商城骨架不能说成全部从零编写。

> 我的项目是一个 Java 微服务与 Python Agent 协作的 AI 商城，面向商品选购和售后两个场景。传统部分包括用户、商品、SKU 库存、购物车、订单、支付和物流；AI 部分让用户可以用自然语言表达预算、偏好和售后诉求，系统通过受控工具访问业务能力。
>
> 架构上，Vue 通过 Gateway 访问领域服务和 FastAPI Agent。Java 服务使用 Spring Boot、MyBatis、MySQL，结合 Redis、RabbitMQ 和 Elasticsearch。Python 复用统一 LangGraph，把导购和售后组织为有界业务分支，通过 MCP 工具连接现有业务接口。
>
> 导购侧我重点完善了结构化需求和多轮条件。模型输出 ShoppingPatch，经 Pydantic 校验后与上一轮条件合并；搜索只负责找候选，Java 再按具体 SKU 校验价格、上架状态、属性和可售库存，返回后才展示推荐。商品对比绑定本轮实际展示的商品及规格，缺失参数明确说明，避免模型猜测。
>
> 售后侧最重要的是把建议和执行分开。系统先查本人订单、政策和资格，再生成服务端提案，前端展示确认卡。用户确认后，Python 读取已保存参数，Java 再次校验归属、状态和重复申请。后续还有人工审核、寄回、验货和模拟退款。对于响应丢失，用原申请标识查询恢复，不能把超时直接当失败重做。
>
> 可靠性上，我梳理了库存操作、Outbox 和 Inbox 的事务边界，并完善分页确定性、分类缓存、结构化工具结果、HTTP 连接资源管理和跨组件关联日志。测试按离线业务、Java 定向回归、真实数据库和在线评测分层，区分 mock 边界和实际验证范围。
>
> 当前演示使用模拟资金，向量检索关闭，正式运费和到账政策等缺少依据时会提示人工核实。我希望这个项目体现的是从自然语言到业务执行的完整工程思路，以及面对重复、超时和状态变化时的处理能力。

这段介绍有五个“可供追问的钩子”：多轮状态、SKU 权威核验、用户确认、未知结果恢复、分层测试。选择你最熟悉的先讲，而不是把所有组件都堆进第一句话。

## 七、哪些说法要纠正？

| 容易说错的话 | 更准确的说法 |
| --- | --- |
| 用 MyBatis-Plus 自动生成所有 CRUD | 当前是 MyBatis Mapper/XML 与自定义 BaseMapper |
| 用 JWT 做无状态登录 | 当前主要是 Redis 中的随机 Token 会话 |
| 导购、售后是两个自主多 Agent 系统 | 统一 LangGraph 平台中的两条有界业务流程 |
| 模型校验了价格与库存 | Java 按业务数据核验，模型只解析/解释 |
| 已验证向量 RAG 与混合召回效果 | 当前向量关闭，本地政策是资料检索；向量效果未验证 |
| Redis 锁保证请求永远只执行一次 | 锁有租约；还依赖 Java 持久幂等与状态恢复 |
| HTTP 超时就是失败，可以重新创建 | 可能已经提交；先查原请求结果 |
| `@Transactional` 保证所有微服务一起回滚 | 本地事务不涵盖远程已提交副作用；Seata 本地关闭 |
| Publisher Confirm 表示业务消费成功 | 只覆盖发布确认，消费与后续副作用另外判断 |
| 已完成真实支付退款 | 本地模拟资金，未验证真实资金到账 |
| 442 个测试都是我新增的 | 既有与新增回归合计，个人新增应指出具体用例 |
| 项目从头到尾完全由我原创 | 基于既有骨架理解并独立实现/增强具体模块，明确自己负责范围 |

## 八、当前尚存边界与验收范围

本次没有为讲解而改动这些行为：真实模型/远程只读整链路评测仍待完成；向量召回效果未验证；可靠签收事件与正式期限、运费、到账依据仍有缺项；换货履约没有实现。已有 Java 规则会处理资料不足，不能让模型补造事实。

交易源码还存在需要继续审计的窗口。例如 `postOrder` 中优惠券处理与库存异常补偿块的先后关系，不能由“库存有补偿”推出所有远程副作用都已统一覆盖。第二讲如实指出这些局限，本次教材没有把发现的问题自动算作已修复。

历史测试详见 [24 号报告](24-数据分页与AI工具可靠性改造报告.md)。文档中的教学并发场景是推演，未重新进行压力测试；平均/P95 的指标定义不是新增测得的数据。

## 九、最终过关标准

你不需要记住所有类名和行号，但应能在一两分钟内找到关键入口。每个核心主题按下面五项各 0～2 分自评：

1. 能用业务语言解释为什么需要它。
2. 能说出真实输入、调用顺序和最终数据位置。
3. 能区分身份、事实、事务与执行边界。
4. 能推演一个故障或竞争场景，并知道现有处理与局限。
5. 能指出验证证据，给出一个替代方案及代价。

总分 8 分以上且第三、四项不为 0，才算可以承受追问。先学第一讲，闭卷回答：“用户发起普通搜索和 AI 推荐，两条链分别经过什么？价格和库存最终由谁决定？”讲顺以后再进入库存事务与售后恢复。
