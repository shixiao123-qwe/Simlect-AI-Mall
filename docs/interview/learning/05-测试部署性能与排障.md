# 第五讲：证明代码正确，解释故障，而不虚报效果

核对日期：2026-11-25。文中的测试数字来自 2026-11-24 留存结果，本次编写教材没有重新运行测试。真实远程链路评测仍待内存条件满足后执行，不能把下面的离线结果说成线上验收。

## 1. “测试通过”到底证明到哪一层？

先问测试把哪些依赖替换了。如果 Java 库存结果是 mock 数据，通过只能证明代码如何处理这份结果，不能证明数据库实际扣减正确。如果测试直接调用图中的业务节点，通过也不能证明浏览器、Gateway、WebSocket、图入口、持久化和退出清理都正常。

| 验证层 | 当前项目的具体证据 | 能证明什么 | 没有证明什么 |
| --- | --- | --- | --- |
| Python 单元/契约回归 | [tests](../../../Simlect-backend/Simlect-agent/tests)、[evals](../../../evals) | 解析、状态、工具契约、错误分支和确认逻辑 | 所有远程依赖真实可用、真实模型理解率 |
| Java 定向回归 | Product/Stock/Order/Gateway 测试 | 指定业务规则、协作与异常行为 | 所有生产事务、集群并发和故障恢复均已实测 |
| 真 MySQL 分页测试 | [ProductPaginationMySqlTest](../../../Simlect-backend/Simlect-product/app/src/test/java/com/simlect/controller/ProductPaginationMySqlTest.java) | 真 SQL 的排序分页集合和回滚清理 | 全库性能、并发快照或生产吞吐 |
| 跨业务离线流程 | [test_business_workflows.py](../../../evals/test_business_workflows.py) | 多轮推荐/对比、提案/确认等真实业务代码协作 | 外部依赖真实联网 |
| 在线只读入口 | [live_business_readonly.py](../../../evals/live_business_readonly.py) | 设计用于真实业务分支 → MCP → Java | 入口存在不代表已经执行通过 |
| 前端行为脚本与类型检查 | web/admin scripts、vue-tsc | 相关逻辑与类型问题 | 实际浏览器每个交互、所有分辨率都正确 |

离线流程将 LLM、MCP 传输、ES、Java 权威结果和 Redis 换成受控边界，真实执行的部分包括图业务分支、结构化条件合并、Router、推荐/对比、提案和确认。这样失败容易复现，能覆盖昂贵或难制造的故障，但需要另做真实集成验证。

### 面试怎么说

“我按边界分层验证。离线用受控结果覆盖异常和多轮状态，Java 测试验证领域规则，再用独立真实数据库测试核对分页 SQL。在线评测单独记录，避免把 mock 的成功率当真实模型或远程链路成功率。”

如果被问“是不是全用 mock，没价值”，可以答：mock 适合隔离责任、稳定复现故障；问题是把它的结论扩大到未执行的边界。两种测试互补。

## 3. 怎样设计一条有价值的测试？

一条测试至少包括：业务前提、刺激动作、可观察结果、不得发生的副作用。不要只断言“调用没有报错”。

例如预算从 300 改为 500：

1. 前提：上一轮保存了类别、全新约束、预算和已展示商品。
2. 动作：输入“预算改成 500，其他条件不变”。
3. 结果：预算变化，其他条件保留；推荐仍用 Java 核验后的 SKU 数据。
4. 负向断言：不能把模型预算修改当成修改商品价格，不能继续引用已被新一轮清空的商品序号。

售后重复确认则要断言：同一提案第二次确认取得相同业务结果，真正的 Java 创建只执行一次；另一个用户不能确认。还要分别构造“确定拒绝”和“执行结果未知”，它们不能用同一个失败状态处理。

故障测试应沿执行顺序插入：写库前、提交后响应前、Java 成功而 Redis 回写前、锁过期后原请求仍运行时。代码里有 `except Exception` 不等于这些场景都正确。

## 4. 指标的分子、分母和时间范围必须讲清楚

### 4.1 五类指标不要互换

| 指标 | 合理定义 | 常见误用 |
| --- | --- | --- |
| 结构化解析准确率 | 有标注需求集中，必需字段和取值满足评分规则的样本占比；同时记录逐字段结果 | JSON 能解析就算意图全部正确 |
| 硬约束满足率 | 有效返回商品中满足预算、上架、指定属性等硬条件的比例；无匹配另行统计 | 删除所有返回商品得到“100%正确” |
| 工具业务成功率 | 明确工具集合、时间窗，以结构化最终状态计算 | HTTP 200 或 MCP 返回文本就算成功 |
| 响应时间 | 明确开始与结束点，如用户发送至最终展示，或单次工具往返 | pytest 用例运行时间当用户延迟 |
| 失败分类 | 解析非法、无候选、无匹配、拒绝、超时、传输、响应异常等分别计数 | 把合理空结果全部当系统故障 |

当前 [run_business_flows.py](../../../evals/run_business_flows.py) 明确输出离线模式，真实模型准确率等不适用字段为 `null`。这比填一个看似完整的数字更有用。

### 4.2 平均值与 P95 怎么理解？

将 n 个耗时升序排列，当前脚本用 nearest-rank 方法取第 `ceil(0.95*n)` 个值，Python 下标再减 1。源码表达式是：

```python
durations[math.ceil(.95*len(durations))-1]
```

平均值可能掩盖少量慢请求；P95 用来描述尾部，但样本只有 8 个时基本接近最大值，统计很不稳定。必须注明样本量、机器、并发、数据规模、冷/热启动和是否调用真实模型。不能拿两次环境不同的单次运行计算优化百分比。

**深入追问：成功率很高但业务体验差，可能为什么？** 成功定义过宽，失败被吞成空结果，少数请求极慢，商品虽合法但不相关，或用户看不到确认/错误反馈。指标要和实际业务验收一起看。

## 5. HTTP 连接池：复用的是连接，不是用户身份

原来每次 Java 内部调用新建并关闭 `AsyncClient`，无法持续利用连接。现在 [internal_http.py](../../../Simlect-backend/Simlect-agent/app/services/internal_http.py) 在应用生命周期内按事件循环管理有界客户端。

真实配置摘录：

```python
return httpx.AsyncClient(
    limits=httpx.Limits(max_connections=12, max_keepalive_connections=6, keepalive_expiry=20),
    cookies=CookieJar(policy=_RejectCookies()),
    follow_redirects=False,
)
```

总连接上限 12，最多保留 6 条 keep-alive，空闲期限 20 秒。这些是当前本机配置，不是压测证明的最佳值。HTTP 连接池也不同于 Hikari 数据库连接池：一个连接 Java HTTP 接口，另一个让 Java 借用数据库连接执行 SQL。

为什么要限定事件循环？异步客户端内部资源与运行循环相关；跨多个 `asyncio.run` 复用可能产生已关闭循环等问题。当前 `_pools` 用 loop 为键。生命周期有引用计数，最后一个 owner 退出后关闭；没有进入应用 lifespan 的 CLI 按请求创建并关闭。

为什么拒收 Cookie？同一个池可能服务多个用户，保存并回放服务器 Cookie 容易把请求状态串起来。请求身份头必须逐次构造，不能 `shared_client.headers.update(user_headers)`。共享网络资源与共享用户状态是两件事。

[main.py](../../../Simlect-backend/Simlect-agent/app/main.py) 用 `AsyncExitStack` 管理启动/退出资源，[ManagedInternalHttpASGI](../../../Simlect-backend/Simlect-agent/app/services/internal_http.py) 绑定 ASGI 应用 lifespan，不是每个 MCP 会话。启动一半失败也要执行已注册的清理，不能等正常停机才关闭。

相关测试见 [test_internal_http_lifecycle.py](../../../Simlect-backend/Simlect-agent/tests/test_internal_http_lifecycle.py)。MCP 协议会话仍按调用建立；不要把 HTTP keep-alive 说成已实现 MCP session 全局复用。

## 6. 超时、重试和取消为什么影响业务安全？

[JavaInternalClient.post_json](../../../Simlect-backend/Simlect-agent/app/services/java_internal_client.py) 按请求传 headers、timeout，检查 HTTP 状态、JSON 形态和 Java ResponseVO 的业务结果，并在 `finally` 记录安全分类日志。

```python
resp = await client.post(url, json=body or {}, headers=headers, timeout=self._timeout)
resp.raise_for_status()
```

HTTP 层检查只是第一步。HTTP 200 里的业务拒绝应识别出来；不含 `data` 或非法 JSON 属于响应契约问题。工具层另用 v2 状态协议区分成功、空结果、拒绝和传输错误，不能靠“错误”两个中文字匹配。

**为什么不自动重试所有 POST？** 调用可能已经落库，只是响应丢失；再次创建可能重复。当前内部客户端不做自动 POST 重试，写操作依靠明确请求标识、Java 持久幂等和结果查询恢复。只读搜索可设计有上限的重试，但也要考虑延迟预算和下游压力。

超时配置也要看所在层。前端默认 HTTP 超时 15 秒，JavaInternalClient 默认 30 秒；聊天发送接口先返回消息标识，后台生成不是要求在这 15 秒内完成。反过来，一个同步写接口可能客户端已超时而服务端还在执行，取消本地等待不会自动回滚远程事务。

**连续追问：一个 30 秒 timeout 是绝对端到端 30 秒吗？** 不能这样概括。HTTPX 的超时涉及连接、读取、写入、池等待等阶段配置；整体工作流还有模型、其他工具和调度时间。若有端到端 SLO，需要专门的总 deadline 和取消传播，并验证副作用恢复。

## 7. Trace ID 怎么连接 Python、MCP 和 Java？

[request_context.py](../../../Simlect-backend/Simlect-agent/app/services/request_context.py) 用 `ContextVar` 保存请求局部关联 ID，ASGI 中间件校验传入格式，没有合法值就生成。核心作用域代码：

```python
token = _trace_id.set(resolved)
try:
    yield resolved
finally:
    _trace_id.reset(token)
```

这里 `token` 是恢复 ContextVar 的句柄，不是登录 Token。`finally reset` 避免请求结束后污染后续任务；后台任务创建时可继承上下文。普通全局字符串在并发请求中会互相覆盖，线程局部变量也不等于协程局部变量。

通过 `X-Trace-Id`，MCP 和 Java 内部调用沿链传递关联。Java 的 [TraceIdFilter](../../../Simlect-backend/Simlect-common/src/main/java/com/simlect/web/TraceIdFilter.java) 放入 MDC，[FeignTraceInterceptor](../../../Simlect-backend/Simlect-common/src/main/java/com/simlect/api/feign/FeignTraceInterceptor.java) 向下游传递。

内部调用日志只记阶段、trace_id、耗时和 outcome，避免记录密钥、完整订单内容、用户身份及原始异常文本。Trace ID 仅用于关联，不提供权限，也不是完整 OpenTelemetry 分布式追踪平台；当前没有因为加一个字段就自动获得所有 span、采样和可视化。

## 8. 分页和缓存为什么也是正确性问题？

### 8.1 同价商品翻页丢失或重复

[ProductController](../../../Simlect-backend/Simlect-product/app/src/main/java/com/simlect/controller/ProductController.java) 当前排序最后追加 `product_id asc`。价格、销量、创建时间相同的商品，如果 SQL 没有确定的最终顺序，分页时可能跨页重复或漏掉。唯一 ID 提供稳定的收尾顺序。

这解决固定数据集的排序确定性，不能保证 offset 翻页期间并发插入、删除仍保持同一快照。数据量大且变化频繁时，可以考虑游标分页或明确快照要求；这些是可选演进，不是当前已完成能力。

### 8.2 分类缓存为什么不能覆盖所有查询？

[SysCategoryServiceImpl](../../../Simlect-backend/Simlect-product/app/src/main/java/com/simlect/biz/impl/SysCategoryServiceImpl.java) 只对无筛选、无分页、无显式排序的完整快照复用缓存。按名称筛选的请求如果直接返回全量缓存，就是错误结果；命中缓存后仍先查库又失去缓存价值。

树形转换使用副本，避免修改缓存对象导致下一次读取受到影响；分类属性批量查询再挂载，减少逐层反复读取。缓存刷新也有边界，不能拿分类缓存策略推断价格和库存永不过期。

**如果面试官问“你加了什么索引”怎么办？** 只讲实际有证据的索引。先找到真实 Mapper SQL，再检查 DDL、查询条件、排序和 `EXPLAIN`。联合索引的列顺序要对应访问路径；不能只因为有 `status` 条件就盲目加一个低选择性单列索引，更不能声称未执行的查询性能提升。

## 9. 16GB 电脑的内存问题应该怎么解释？

不要把 `Xmx` 总和当项目总占用。JVM 还有线程栈、元空间、代码缓存、直接内存及其他本地开销；Docker/WSL 里的中间件、Python、Node、IDE 和操作系统也在使用内存。物理空闲与提交内存余量不同：页面文件能提供提交空间，但频繁换页可能让响应明显变慢。

[Get-LocalServicePlan](../../../deploy/local-stack-common.ps1) 当前 full 模式十个 Java 服务，堆上限合计 2176MB。配合 SerialGC、两核、较小线程栈和代码/直接内存上限降低单机负担。这些是本地演示取舍，不能直接作为生产参数模板。

| 本地场景 | Java 服务范围 | 适合验证什么 |
| --- | --- | --- |
| guide | User、Product、Stock、Search、Gateway | 搜索、导购、对比；订单和售后不保证可用 |
| after-sale | 除 Search 外九个服务 | 交易与售后；需要搜索时切 full |
| full | 十个服务 | 完整本地功能组合，资源压力最大 |

`Assert-LocalMemoryBudget` 以 4GB 物理余量为提醒目标，硬保护至少 1GB；具体启动前还有更高的物理/提交预检。它是检测与阻止继续分配，不会凭空释放内存，也不能保证运行过程中其他软件不继续占用。

[test-local-memory-safe.ps1](../../../deploy/test-local-memory-safe.ps1) 以分时方式运行测试，管理启动器登记且能确认归属的进程，并按原场景恢复。不能为了腾内存任意结束用户其他任务。

本地数据库端口当前使用 3307，避免与系统 MYSQL80 的 3306 冲突；[本地端口覆盖配置](../../../deploy/docker-compose.local-port.yml) 保留数据卷。出现端口冲突时应明确改的是宿主机映射与客户端连接，不是把所有 MySQL 服务的容器端口都随意改掉。

## 10. 面对“网络异常”，按证据排查

按最早失败的边界查，避免一出错就重装 Docker 或清数据库：

1. 浏览器 Network 看真实 URL、HTTP 状态、响应内容和业务码。确认发的是 `/api` 还是 `/admin-api`，当前访问的是哪个端口。
2. Vite 报 `ECONNREFUSED`，先检查代理目标和 Gateway 是否监听，尚不能据此断定商品库没数据。
3. Gateway 可达而下游不可用，检查路由、Nacos 实例和领域服务健康。健康 UP 只覆盖其配置的检查项，不保证真实模型、每条 MQ 消费或完整售后正确。
4. 领域日志出现 SQL/连接异常，核对 JDBC 地址、端口、库名、权限和中间件健康。不要在日志里输出密码。
5. AI 工具失败按结构化 errorCode 区分：没有商品、无匹配、Java 拒绝、Java 超时、MCP 传输失败、响应格式异常。Trace ID 串联同一次请求。
6. 写操作超时先查原请求状态；确定未执行与未知结果必须分开，再按确认/恢复机制处理。

日志通常位于启动输出给出的 `logs/local-stack/<时间>/`，定位本次运行目录，不要打开上周旧日志误判当前故障。密钥认证成功、模型名称可用、额度充足仍需真实调用证据，单个 `/health` 不能证明。

## 11. 面试连续追问与参考回答

**问：你说测试 442 条，都是你新写的吗？** 不是，是既有与新增回归的合计；我会指出本轮修改关联的测试文件和具体新增场景，不把总数作为个人新写数量。

**追问：8 条流程用例与单元测试差在哪？** 它们串起多个真实业务组件，但外部边界可控；能验证多轮状态和调用结果协作，不能代替远程整链路。

**追问：怎么验证模型真的理解“预算改为 500”？** 需要有标注多轮集和真实模型运行，记录字段级与整例准确率；脚本化解析只验证后续链路。

**问：连接池为什么更可靠？** 复用连接减少重复建连，资源有上限，生命周期结束能释放；身份与 Cookie 隔离避免跨用户污染。没有基线时只说机制改进，不报加速百分比。

**追问：12 个连接够吗？** 这是当前本地限制，不是通用最优值；应结合并发、平均服务时间、池等待和下游容量测量调整。

**问：工具调用成功率怎么统计？** 按最终结构化业务状态，而非传输完成；empty、denied、legacy、transport_error 分开，先定义分母和观察窗口。

**追问：返回空列表算失败吗？** 正常无匹配是有效业务结果，和后端故障不同；需要同时观察召回覆盖和约束满足率，不能全空刷准确率。

**问：有 Redis 锁还需要数据库幂等吗？** 锁会过期或进程会崩溃，数据库请求标识和约束承担持久防重；恢复时还要能查原操作结果。

**问：你压测到多少 QPS？** 当前材料没有同条件压测与生产容量证据，不能报告 QPS。可以说明测试分层、当前资源限制、下一步压测设计和需要观察的瓶颈。

**问：为什么不再引入监控平台？** 单机资源有限，先补结构化结果、关联 ID、必要计数和报告，能够定位问题；后续规模需要时再接完整观测体系。
