# 04｜售后确认状态机与故障恢复：从一张确认卡读懂 AI 业务安全

本章依据 2026-11-25 工作区源码编写，目标是让你能解释一笔售后申请如何获得授权、如何避免重复提交，以及网络异常后凭什么判断结果。阅读本章不需要先背分布式理论，但要始终区分三个事实：用户是否同意提交、申请是否写入数据库、售后是否已经履约。它们由不同状态表达，不能用一个“成功”概括。

这是源码学习材料，本轮只读代码和编写文档，没有启动服务或执行测试。历史改造边界可对照[售后规则阶段报告](../21-售后Agent规则完善阶段完成报告.md)和[可靠性改造报告](../24-数据分页与AI工具可靠性改造报告.md)；具体行为以本章链接的方法为准。

## 一、先建立职责边界：AI 可以提出申请，不能把建议变成资金操作

可以先用这段话介绍功能：用户通过聊天查询本人订单、物流和售后政策，选择订单明细、类型及原因后，系统生成服务端提案。用户点击确认，Python 才携带当前登录身份调用 Java。Java 再次校验归属、状态和重复申请，把申请写为待审核。后续审批、寄回、验货和退款是另一条履约链，仍由 Java 控制。

这里的“再次”很重要。用户看到确认卡到点击确认之间，订单可能发货、申请可能被其他入口提交。提案阶段查过资格，并不意味着执行阶段可以省略检查。AI 输出中的“可以申请”也不是批准退款，更不是资金到账。

本项目不是让一个售后模型随意规划所有步骤。[after_sale_turn.py](../../../Simlect-backend/Simlect-agent/app/services/after_sale_turn.py) 的 `after_sale_intent` 和 `after_sale_turn` 是有界业务分支，复用统一 LangGraph。含“政策、多久、运费”等表达时先走政策分支；含申请语义、订单项和原因时才可能走提案。没有理由会追问，没有订单项会要求用户选择。它不会因为某一订单只有一件商品，就自动把“查询”解释成“同意提交”。

例如“退款规则是什么”读取政策；“这项可以退吗”检查资格；“申请退货退款，原因：商品损坏”才进入提案准备。很多路径由明确规则执行，并非每次都让模型自由选工具。面试时应说“模型能力与有界业务流程结合”，不要说“售后全部由大模型自主决策”。

## 三、先分清三个标识与三个时间

`actionToken` 是形如 `act_...` 的提案索引，用于取回 Redis 记录；`requestId` 是一次业务申请的稳定标识，最终成为数据库主键；`userId` 表示该提案所属用户。二者都看起来像随机字符串，也不能互换。关联日志的 `traceId` 更只用于排查，不具备授权或业务幂等作用。

`create_pending` 保存的主要字段包括 `token`、`userId`、`messageId`、`actionType`、`requestId`、`paramsJson`、`summary`、`status`、`createTime`、`expiresAt`。`paramsJson` 中的编号会与顶层编号一致；售后参数含订单项、类型和原因。后续确认读取这些原参数，而不是让浏览器重新拼装一笔申请。

第一种时间是确认窗口。[constants.py](../../../Simlect-backend/Simlect-agent/app/constants.py) 的 `PENDING_ACTION_TTL` 是三十分钟，记录的 `expiresAt` 用于判断尚未执行的卡片能否首次确认。到期瞬间也算过期。第二种时间是记录保留期，`RESULT_TTL` 是七天，方便查已执行结果。第三种是执行锁租约，确认默认一百二十秒，取消默认三十秒。

三十分钟并不意味着三十分钟后删除全部恢复证据；七天也不是七天内随便点都能首次执行。Redis 保留期更不是永不丢失的业务账本，宕机、淘汰或人为删除都可能使缓存缺失。数据库中的原申请才是提交事实。记录丢失后不能声称系统一定能自动重建原提案，正确处理是核查本人申请进度，必要时转人工。

## 四、最容易被问错的状态：数字零到六只描述确认操作

以下数字来自 `PendingActionService`，不要套用到订单或退款表。

| 数字 | 名称 | 精确含义与下一步 |
| --- | --- | --- |
| 0 | PENDING | 服务端提案已存在，等待确认；可确认、取消或过期 |
| 1 | SUCCEEDED | 已核验原申请提交成功；历史别名为 CONFIRMED，不等于已退款 |
| 2 | CANCELLED | 提交前取消，保留结果，不调用 Java 创建申请 |
| 3 | EXPIRED | 尚未执行的确认窗口已过，不允许首次提交 |
| 4 | EXECUTING | 提交中或已有执行者，不允许并发再写 |
| 5 | FAILED | 明确的业务拒绝，当前记录不会自动重试 |
| 6 | UNKNOWN | 无法确定远端提交结果，必须查原请求，不等于失败 |

`ActionResult.success` 只有状态一才为真。因此 HTTP 返回二百、响应外层格式正常，与业务 `success=true` 是不同层次。限流、无权限、正在执行、结果未知都不能伪装成申请成功。

还要区分 SQL 的两层状态。`after_sale_request.status` 只允许 `PENDING_REVIEW`、`APPROVED`、`REJECTED`、`COMPLETED`；`after_sale_fulfillment.phase` 细分 `WAIT_RETURN`、`WAIT_INSPECTION`、`READY_REFUND`、`REFUNDING`、`REFUND_FAILED` 等履约步骤。`AfterSaleWorkflowMapper` 用 `COALESCE(f.phase,r.status)` 展示尚未建立履约行的申请。

所以，同一时刻确认操作可以是数字一，申请仍是 `PENDING_REVIEW`；申请是 `APPROVED`，履约仍是 `WAIT_RETURN`。待寄回不是审批失败，审批通过也不是退款完成。业务订单另有数字状态，例如订单状态六表示全额退款关闭；它绝不能被误读成确认操作的六 `UNKNOWN`。订单明细的零又表示已退款，不能理解成待确认。

## 五、owner 锁、CAS 与数据库幂等分别防什么

Redis 执行锁首先解决“谁来处理同一张卡”。`try_lock_pending_action` 用 `SET NX EX`：仅在锁键不存在时写入随机 `owner` 并设置租约。返回空表示没抢到锁，确认接口给出处理中，而不再调用执行器。`unlock_pending_action` 用 Lua 比较当前持有者后再删除，防止旧请求租约过期，误删新请求的锁。

CAS 解决“处理时读到的状态还成立吗”。下面是 Redis Lua 中的真实六行摘录，不是完整脚本：

```lua
if tostring(obj['status']) ~= expect then return 0 end
local patch = cjson.decode(ARGV[4])
for field, value in pairs(patch) do obj[field] = value end
obj['status'] = tonumber(target)
redis.call('set', key, cjson.encode(obj), 'EX', ttl)
return 1
```

`obj` 是 Redis 中原提案，`expect` 是调用者预期的旧状态，`target` 是目标状态；`patch` 包含结果文案等附加字段，`ttl` 是更新后的保留时间。比较、修改状态、写结果文案在一次 Lua 执行内完成，避免先读后写被其他请求插入。键缺失、状态不同、数据非法都不会获得修改成功的返回值。

但锁会过期，Redis 状态也可能丢失。两个不同 `actionToken` 甚至可能针对同一个订单项，令牌锁无法互斥它们。因此不能说“有 Redis 锁就保证永不重复”。本项目再用 Java 的稳定 `requestId`、订单及明细行锁、重复参数核对、活跃申请唯一约束兜底。锁减少竞争，CAS 控制流转，数据库保证业务不变量，职责互补。

文件里还保留 `try_mark_pending_executing` 和清除旧执行标记的辅助方法。当前 `confirm` 的主执行资格依赖 owner 锁与提案状态 CAS，不能仅看到旧 `exec:` 键方法，就把它误当作完整安全设计。

## 六、确认接口逐步执行：先验归属，再有条件地写业务

`confirm_action` 先通过 `require_login` 得到当前用户，同时获取当前请求的用户登录 token。它把执行函数和结果查询函数作为回调交给 `confirm`。确认参数只有提案索引，不由模型提供“现在使用哪个用户身份”。

`confirm` 在尝试加锁前就调用 `load_owned`。即使另一用户正占着锁，错误用户也只能得到无权操作，不能借处理中状态探测结果。拿锁后再次读取并验归属，防止此前快照已经改变。已有明确终态可直接返回，重复点击不是每次重新调用 Java。

首次确认从零开始：检查确认期限；只读恢复请求不执行；真正确认先用 CAS 将零改为四，成功者才调用执行器。旧代码曾把 `CONFIRMED` 置一后再执行，所以状态一但没有结果文案的历史记录不被当作提交成功，而转入结果核实。这体现了升级兼容需要理解“旧字段当时表达什么”。

执行器明确返回正常业务结果，才尝试把四改为一。明确业务拒绝以 `ValueError` 进入五；网络异常、响应异常等无法证明未提交的异常进入六，并尝试查原结果。这里的分类依赖可信 Java 业务契约，不能把所有异常都包装为 `ValueError`，否则会丢掉恢复机会。

`cancel` 也先验归属，再获取 owner 锁，只允许 CAS 从零改为二。已经执行、未知或已处理的卡片不能用取消来“抹掉”。取消提案与撤销售后申请不同，更不等于撤回已经发出的资金请求。

## 七、Java 如何证明“还是原来那笔申请”

[AfterSaleDTO.java](../../../Simlect-backend/Simlect-order/app/src/main/java/com/simlect/entity/dto/AfterSaleDTO.java) 的 `Create` 只允许请求编号、订单项、类型和原因；没有退款金额、资格通过标志和用户编号。Python `_after_sale_payload` 同样只取这四个字段，还核对顶层与参数中的编号。Java Controller 再从登录上下文取得用户，不相信模型塞入的 `userId`。

`create` 先查订单项及本人订单，然后按固定顺序取得行锁。真实摘录如下：

```java
OrderInfo order=applications.lockOrder(firstOrder.getOrderId());
OrderItem item=applications.lockItem(dto.orderItemId());
```

`order`、`item` 是当前事务锁内重新读取的业务行；`firstOrder` 是先前用于定位的订单，不能作为最终校验快照；`dto` 仍是原用户提案。锁后再次核对订单所属用户及明细所属订单，避免查到了明细却忽略其父订单权限。

随后按 `requestId` 查原申请。存在时比较 `userId`、`orderItemId`、`type` 和去掉首尾空格的 `reason`，一致才返回原记录；同编号不同参数不能被当成安全重放。不存在时再检查当前业务状态及处理中申请，成功后在同一事务插入申请与操作日志，任何异常都回滚本地事务。

数据库还有独立约束，来自真实建表 SQL：

```sql
 active_item_id varchar(40) GENERATED ALWAYS AS (CASE WHEN status IN ('PENDING_REVIEW','APPROVED') THEN order_item_id ELSE NULL END) STORED,
 UNIQUE KEY uk_after_sale_active_item(active_item_id),
```

`active_item_id` 只在申请处理中等于订单项 ID，其他状态为 `NULL`。唯一键防止不同请求编号同时创建同明细的处理中申请；已结束申请仍可保留历史。它与请求主键分别约束“同一次请求”和“同一业务明细”，不能互相代替。

上述真实摘录共十行。其余流程说明均为源码解释，不把简化叙述冒充完整可执行实现。

## 八、结果恢复：查原 requestId，而不是自动再申请一次

`_validate_application` 不是只看 Java 返回“成功”。它要求响应中的 `requestId`、`orderItemId`、`type` 与原 payload 一致，并且有申请状态。收到另一笔申请、空对象或坏 JSON 都不能宣布成功。坏响应无法证明 Java 没提交，因此执行桥接把它作为需要核实的异常处理。

`ActionExecuteService.recover` 对售后申请调用 `/api/order/afterSale/result`，仍使用当前用户登录 token 和原四字段。Java `AfterSaleService.result` 采用 `READ_COMMITTED` 事务，并按与创建相同的顺序加锁、核对权限、检查原编号及参数。它不插入申请。若前一次创建事务正在进行，相同业务锁有助于查询等待其结束，再读取提交事实。

查询返回 `SUCCEEDED`，含义是原申请曾提交成功，即使现在已审核、驳回或履约完成，创建事实仍然成立。返回 `NOT_FOUND` 只代表当前查不到，同时 Java 按现有资格给出 `retryAllowed`。原网络请求仍可能晚到，故“没查到”不能等同“原请求永远不会执行”。

前端的 `getActionResult` 调用 `confirm(..., recover_only=True)`：无论查到什么都不提交业务。它可以在状态六中提示允许重试，但用户必须再次明确点击确认；下一次确认仍先查结果，只有售后类型、查询为 `NOT_FOUND` 且明确允许重试时，才复用原编号和原参数执行。不能生成新编号绕过同一请求的幂等入口。

确认收货、评价等旧操作没有相同的按请求编号结果账本，`recover` 返回未知，不能借用售后的重试许可。幂等与恢复能力是接口契约，不是给任意 POST 加一个字符串就能通用。

## 九、四个故障推演：面试官会追问到哪一步

### 场景 A：Java 已提交，HTTP 响应丢失

用户点确认，Redis 从零变四，Java 事务写入待审核申请并提交；回包途中超时。Python 只能知道没收到结果，先写六再查原编号。若查到同参数申请，就返回提交成功并尝试缓存一和结果文案。查询也超时则保持未知，页面提示查进度，不能说失败、不能另生成申请。恢复后人工审核仍未发生，绝不能把“申请找到了”描述为“退款到账”。

### 场景 B：重复点击与锁租约过期

同一张卡同时点两次，第一请求抢到 owner 锁，第二请求返回执行中。第一请求结束后，后续点击命中已有结果。若第一请求超过锁租约，第二请求可能获得新锁，此时不能依赖 Redis 锁声称没有并发。它应根据四或六先查原结果，必要的显式重试继续使用原编号，最终由 Java 行锁、参数核对和唯一约束保证不能创建两条相同业务的活跃申请。

原请求最后释放锁时必须比较 owner，不能误删新持有者的锁。这里没有凭空的“无限续期”和“严格恰好一次”，是多层检查抵御常见重复执行窗口。

### 场景 C：Java 已成功，Redis 结果保存或解锁失败

`_finish` 的缓存写入出错会记录告警，但仍返回已核验的业务结果；清除旧标记和解锁也各自捕获异常，不覆盖成功返回。即使 CAS 因状态变化没有落成目标值，也不能据此断言 Java 失败。下次查询看到旧四或六，可以按原编号恢复。必须监控这些告警并核查存储状态，但不能为了让缓存看起来一致而重复执行业务。

### 场景 D：不同用户、旧订单和会话串用

用户甲拿到乙的提案索引，`load_owned` 在加锁前就拒绝；即使 Python 上层有缺陷，Java 写申请入口的用户 token 和订单归属还应拒绝创建。内部 token 只是服务凭证，不能代替用户授权；当前一些内部只读接口信任服务传入的 userId，因此共享令牌泄露且端点可达时仍有身份冒用风险。不能由写入口的用户校验推导所有内部读接口都独立验证终端用户。

同一用户换了订单也有风险。`after_sale_turn` 遇到显式新订单但没有订单项，会清除旧售后上下文；订单项变化也不继承旧原因等待状态。仅在当前用户确实处于补充原因场景时，单独一句“原因：……”才使用旧明细。会话记忆按用户存储，不应声称不同浏览器标签页天然是独立会话。

[agent_engine.py](../../../Simlect-backend/Simlect-agent/app/services/agent_engine.py) 对同用户推理设置一百八十秒锁，图执行总超时一百五十秒，并比较消息编号，减少并发整份状态覆盖；这与确认卡锁不是同一个锁。锁租约、消息顺序和业务归属都需要分别解释，不能统一叫“加了 Redis 就安全”。

## 十、人工审核、寄回、验货与退款为什么是另一条状态机

管理员接口在 [AfterSaleAdminController.java](../../../Simlect-backend/Simlect-order/app/src/main/java/com/simlect/controller/admin/AfterSaleAdminController.java) 中校验管理员登录，对审核、验货、退款还有 `AdminSensitiveConfirm`。普通用户的售后确认不能代替管理员审批权限。

`review` 拒绝已经结束的申请。批准前重查订单归属、明细是否正常、是否符合未发货退款或退货条件；退货还要求配置地址。未发货退款批准后到 `READY_REFUND`，退货退款批准后到 `WAIT_RETURN`。不能看到申请状态 `APPROVED` 就跳过寄回验货。

用户调用 [AfterSaleProgressController.java](../../../Simlect-backend/Simlect-order/app/src/main/java/com/simlect/controller/AfterSaleProgressController.java) 的 `returnParcel`，只有本人、已批准、待寄回、退货退款类型才可登记物流。填了单号只进入 `WAIT_INSPECTION`，不是系统已验证真实包裹。管理员 `inspect` 再决定通过或驳回，拒绝验货时不能标成可回补库存；损坏商品不能自动恢复可售数量。

`refund` 先检查执行开关及支付单号，再使用支付单生命周期锁。正常管理员入口没有外层事务，因此先提交一笔绑定 `refundReference` 的本地事务，再进入后续执行事务。当前 `TransactionTemplate` 没有设置 `REQUIRES_NEW`，其他调用环境仍须核对传播行为，不能泛称任意入口都会独立提交。正常入口下，这样可在后续回滚或 Redis 锚点过期时找回原退款单号。它不把外部支付和 MySQL 伪装成同一个原子事务；失败后用原单号核实和恢复。

实际执行还核对申请阶段、订单资金模式、订单明细退款结果及金额。组合支付只有所有关联子订单都已退款，才把支付单整体标为退款。执行失败可能转 `REFUND_FAILED`，这表示需核实并复用原退款编号，不是可以换个编号再退一次。退款开始或结果待核实后，审核也不能随便驳回并释放活跃申请。

本地模拟模式用 `LOCAL_DEMO_` 渠道标识与配置互相核对，`simulated` 字段及结果文案说明没有真实资金退回。即使非模拟代码路径存在，“渠道受理”和“用户实际到账”也不是相同事实；当前没有正式到账时效承诺。

## 十一、政策检索与七天规则：知道未知，比编造承诺更重要

[after_sale_policy.py](../../../Simlect-backend/Simlect-agent/app/services/after_sale_policy.py) 的 `query_policy` 读取本地 JSON，以关键词命中后返回原文，附来源、版本和 `AS-004` 限制。它还校验语料结构，缺少限制文档或文件异常时返回暂不可用。它是本地词项检索，不是已经验证效果的向量 RAG，也不是每一次资格判断前必然先调用的独立审批模型。

[AfterSalePolicyRules.java](../../../Simlect-backend/Simlect-order/app/src/main/java/com/simlect/biz/AfterSalePolicyRules.java) 有期限计算器，输入必须包含有来源的配置、可信签收时间、商品适用性和服务器时间。默认天数为零、来源为空。当前 `AfterSaleService.decision` 明确传入缺失签收事实和未知适用性，返回 `APPLICATION_ONLY`、`POLICY_MISSING` 等说明。

现有物流表没有可靠签收字段；轨迹文字和下单时间都不能替代。普通商品期限、运费承担、退款到账时间缺正式依据时继续人工核实。`exchange` 虽在类型和表约束中存在，审核方法仍拒绝批准换货履约，因为没有完成换出库存及发货链路。面试时说“算法可测、事实未接入、换货履约未实现”，比说“完整智能客服”更准确。

## 十二、连续二十问：按同一业务场景层层回答

下面不是二十个孤立名词。请让同学扮演面试官，从第一问连续追到第二十问，每题先口头回答，再看参考。

**1．为什么售后需要 Agent？** 为用户把自然语言问题转成订单、政策、资格和提案操作，降低寻找业务入口的成本。业务规则不因此交给模型；Java 仍控制事实、权限和写入。

**2．你是让模型直接决定能不能退款吗？** 不是。工具读 Java 的申请资格，提案只进入人工审核。期限依据缺失时明确表示未知，不把生成文本当审批结果。

**3．模型说“已帮你申请”就算提交了吗？** 不算。必须有服务端保存的提案，经用户确认调用 Java，核对返回的原请求编号、明细、类型和状态后才表示提交成功。

**4．为什么确认卡不能把订单、金额都交给前端重传？** 前端可以被修改，模型也可能编造。确认接口按索引取回服务端原参数，Java 从登录身份确定用户，退款金额由真实订单计算。

**5．actionToken 与 requestId 有什么不同？** 前者查提案和确认状态，后者标识稳定业务申请。卡片索引不能代替登录身份，业务编号不能在重试时随机重建。

**6．两个人拿到同一张卡会怎样？** 提案先校验所属用户，非本人在竞争锁之前就拒绝；Java 创建和结果查询又根据当前登录用户核对订单归属，不能只靠随机索引难猜。

**7．同一用户连续点两次呢？** 先用带 owner 的锁限制并发，再按提案状态 CAS 选出执行者；有结果返回已有结果。不同提案仍可能冲突，所以还有数据库约束。

**8．锁过期还谈得上幂等吗？** 不能只谈锁。租约过期允许另一请求进来，但它查原结果、沿用原编号，Java 行锁和唯一约束继续守住业务边界。释放时比较 owner 防误删新锁。

**9．CAS 与事务是否一样？** 不一样。Redis Lua 原子更新缓存中的状态与结果字段，不能让 Redis 与 Java 数据库一起提交。业务事务和恢复查询解决的是另一层问题。

**10．Java 完成后超时，你返回失败吗？** 返回未知并查询原申请。超时只证明客户端没及时收到响应，不证明数据库未提交。直接提示重来可能制造重复操作。

**11．查结果没查到，为什么还不直接重试？** 它只是当前快照，原请求可能晚到。只读查询先给出重试资格；用户再次明确确认后，仍用原编号和原参数走 Java 幂等门。

**12．只读结果接口怎么保证不写？** Python 的 `recover_only=True` 不调用执行器；Java `result` 只加锁、校验、查询并返回恢复状态，不执行插入。它与创建接口分开。

**13．为什么结果查询也加锁？** 与创建使用相同的订单、明细锁顺序，能等待正在进行的本地创建事务，并在合适隔离级别读取提交结果。它不能阻止尚未到达的网络请求，故仍需稳定编号。

**14．同一编号换一个原因会怎样？** Java 比较用户、订单项、类型和规范化原因，不一致就拒绝，不能把不同意图当重复请求。需要新的用户提案时应重新确认，而不是篡改恢复载荷。

**15．数据库怎么拦住两张不同卡？** 两张卡有不同编号，主键不冲突；活跃明细生成列及唯一键仍防止同一订单项同时存在两条处理中申请，锁内资格检查也会拒绝后到者。

**16．Java 成功但 Redis 写结果失败呢？** 保留已核验成功的返回，记录缓存告警；之后按原编号重建结果。不能让缓存故障推翻业务提交事实，更不能为了修缓存再次执行。

**17．为什么审核通过还没退款？** 申请状态表示审批，履约阶段表示后续工作。退货需等待寄回和验货，未发货退款也要管理员执行资金步骤，两条状态不能混成一个成功标记。

**18．Redis 的 SUCCEEDED 和 SQL 的 COMPLETED 哪个算结束？** 前者结束本次确认提交，后者结束售后履约。申请提交成功时 SQL 可以仍待审核；查询恢复也不应把已驳回申请误说成退款成功。

**19．你们已经做了七天无理由和向量知识库吗？** 当前只有可测试期限算法及本地政策原文检索，没有可靠签收事实与正式条款接入，不能承诺在线七天判断；向量 RAG 的效果也未验证。

**20．最重要的技术难点是什么？** 在网络、缓存和业务事务不能原子提交的条件下，保留原始用户意图，区分未知与明确失败，用用户确认、稳定请求编号、Java 幂等及结果恢复形成可解释闭环。没有宣称严格恰好一次或真实到账。

## 十三、练习、评分与常见错误说法

先做源码定位练习：十分钟内指出提案的创建方法、第一次零到四的 CAS、原申请结果查询和数据库活跃唯一键。每处不仅找名字，还要说明输入来自谁、失败后是否允许写业务。四处各五分，共二十分。

再做故障演算：画出响应丢失、重复点击、结果缓存失败、跨用户确认四种时间线。每种要写出确认数字状态、Java 是否可能已提交、下一步调用哪个只读接口、是否允许自动重试，四题共四十分。把“网络超时就是五”或“查不到直接新建”作为关键错误。

最后练二十问，每题两分，共四十分。一分给正确结论，一分给可定位的方法、字段或异常分支。将源码定位二十分、故障演算四十分、二十问四十分相加，总分一百分。总分八十分以上才进入连续追问训练；六十到七十九分说明能讲流程但恢复边界不牢，先重读第七至九节；低于六十分先不背“高可用、幂等、分布式锁”等词，亲自画一笔申请。

常见错误与修正：

| 错误说法 | 应改成的表达 |
| --- | --- |
| 用户输入退款就自动退款 | 明确类型、明细、原因后先出提案，确认后只提交申请 |
| 有内部 token 就能代表任意用户 | 内部身份与用户业务授权分层，写接口仍取用户登录上下文 |
| Redis 锁过期说明上一次失败 | 租约过期只说明锁不再有效，业务结果仍需查原编号 |
| 状态一是退款成功，状态六是订单关闭 | 数字属于确认状态；SQL 申请、履约与订单各有独立枚举 |
| 重试就是重新生成一个请求编号 | 售后恢复保留同一编号与参数，先查结果再显式重试 |
| 缓存保存失败就把整笔退款撤销 | 缓存不能回滚已提交业务，应恢复可验证结果并告警 |
| 七天算法有测试就已经接上真实政策 | 缺事实或正式条款仍不能在线判断，未知必须说未知 |
| 模拟退款完成等于用户已到账 | 演示没有真实资金变化，渠道受理与实际到账也需区分 |
