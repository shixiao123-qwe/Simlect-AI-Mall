# AI 导购 2.0 实现与验收

## 这次改了什么

原项目已有普通关键词/向量/RRF召回、批量商品快照、会话记忆、MCP工具、商品卡片。此次复用它们，新增结构化需求、严格SKU筛选、序号对比和评测。原普通搜索仍然保留；本地关闭向量时只走关键词召回。

### 1. 需求模型与多轮更新

`Simlect-backend/Simlect-agent/app/models/shopping.py`：ShoppingRequirement、ShoppingPatch、HardAttribute。

金额用 Decimal，非负、最多两位小数、上下限有序，额外字段拒绝。用户可说“成色全新”，对应 hard_attributes；“最好低延迟”对应 preferences，不自动猜测延迟阈值。category是检索词，不是模型臆造的分类ID。

`app/services/shopping_parser.py#parse_shopping` 调用现有 create_memory_llm().with_structured_output(..., method="json_schema")，20秒总超时，再经过Pydantic和合并校验。用户文本作为JSON数据放在HumanMessage中；失败仅返回异常类型，不写用户文本/密钥到新增日志。

未提及字段为null，保留原值；clear显式清除；reset更换品类。ShoppingPatch列表允许null，避免结构化输出中“空列表默认值”抹掉原偏好。合并后重新验证区间。

`app/services/shopping_turn.py#shopping_turn` 复用 session_memory_service 的 Redis/MySQL 会话 state，存 shoppingRequirement 和 shoppingResults。请求订单/退款/券等意图优先，不因上轮有预算就劫持会话。解析失败转原 SEARCH_PRODUCTS，并明确提示“预算和属性未核验”；清空严格商品指代列表。

### 2. Java 按SKU核验

`Simlect-backend/Simlect-product/app/src/main/java/com/simlect/entity/dto/AiProductFilterDTO.java`：最多50个候选商品ID、金额、分类/品类词、最多10个属性约束，Bean Validation。

`.../controller/internal/ProductInternalController.java#aiFilter`：POST `/internal/product/ai/filter`，复用内部鉴权与ResponseVO。

`.../biz/AiProductFilterService.java#filter`：复用 ProductInternalService.snapshotBatch 的商品/SKU/属性批量查询；上架状态来自Java，价格来自具体SKU；按候选品类词匹配真实分类名或商品标题；硬属性必须在对应SKU的propertyValueIds中找到精确name/value证据。SKU属性ID实际使用 `-` 分隔。没有成色数据时，不把“全新”当成满足。

商品、SKU与属性先分组，避免对所有商品反复扫描全体SKU/属性。候选SKU超过5000拒绝。分类当前通过一批分类查询匹配，不依赖模型分类ID。

库存新增只读批量接口 `/internal/stock/readBatch`：

- `Simlect-stock/api/.../dto/StockReadBatchDTO.java`
- `api/.../StockFeignClient.java#readBatch`
- `api/.../support/StockFeignSupport.java#readBatch`
- `api/.../fallback/StockFeignFallbackFactory.java`：失败返回不可用，不能默认有库存。
- `app/.../controller/internal/StockInternalController.java#readBatch`
- `app/.../biz/SkuStockService.java#readBatch`
- `app/.../mappers/SkuStockMapper.java#selectByProductIds` 与对应Mapper XML：按product_id IN一次查，使用主键前缀，去重、上限50商品/5000SKU。

Product通过一次Feign批量请求获得SKU库存，缺失库存按0排除。推荐库存只是查询时快照，不预留；下单仍走原锁库存、扣减和支付流程。

### 3. LangGraph → MCP → Java

新链路：原 build_context意图解析 → agent_loop首轮 shopping_turn → Pydantic需求更新 → MCP RECOMMEND_PRODUCTS → shopping_service.recommend → 关键词+向量RRF候选 → JavaInternalClient显式HTTP请求 `/internal/product/ai/filter` → Java真实SKU筛选 → 仅对合格结果做偏好排序 → 复用商品卡片。

`app/graph/nodes.py` 接首轮分支，`app/graph/state.py` 增shopping_requirement/shopping_handled。

`app/mcp_server/server.py` 注册 RECOMMEND_PRODUCTS、COMPARE_PRODUCTS；`app/harness/guardrails/tool_guard.py` 加只读白名单；`app/services/mcp_tool_router.py` 增参数规范化并沿用登录用户覆盖规则。新工具由服务端图路由调用，避免模型生成候选ID；不改变原模型普通工具集合。

`app/services/shopping_service.py` 复用 rag_retriever 与rrf_merge，候选最多40；推荐总超时25秒，Java HTTP超时10秒。强制内部HTTP模式，DB兼容模式拒绝新推荐路径。结果排序仅匹配Java已返回的属性证据；无证据明确说明，不由LLM编造优点。每商品展示一个匹配SKU，先偏好分，再价格、ID稳定排序。

### 4. 为什么必须改finalize

原 `app/services/agent_runtime.py#finalize_agent_response` 有“没卡片再补搜/热销”的恢复路径。新 shopping_handled 分支直接把已核验结果/无结果文本推送与落库，禁止普通补卡。对比说明直接放现有PRODUCT_SEARCH_RESULT.intro，避免普通简介长度截断第三款对比。

这不是删除原搜索兜底：只有严格导购路径隔离，原普通聊天/浏览继续原行为。

### 5. 商品对比

“第一款和第三款哪款适合游戏”由 comparison_indices 提取序号；只能映射上一轮严格推荐已展示的 shoppingResults，最多2～3款，不接受模型自造ID。Java重新读取真实价格、库存、属性。

COMPARE_PRODUCTS返回每商品匹配SKU价格/库存、参数、可证实推荐理由；缺参数/缺点明确“暂无数据”。无库存、下架、不存在统一显示暂无可比较数据，不猜测。

限制：当前序号支持第1～8款/个/件；不含上一轮普通搜索结果的迁移、任意口语指代与跨页选择。对比展示各商品按偏好排序选出的一个可售SKU，不是所有SKU的笛卡尔比较。模糊硬属性不自动做近义推断，避免误判；可能返回保守的空结果。

## 面试解释

问：为什么不用模型直接筛价格？答：LLM只提取用户意图；索引和模型都不掌握实时业务状态。Java用BigDecimal比较具体SKU，并通过Stock批量接口核库存，结算时再校验。

问：预算提高后怎么知道原偏好仍保留？答：我使用Patch语义，未提及为null、取消走clear、换品类走reset；合并后重新校验，单测覆盖保留与清除。

问：RAG没召回正确商品怎么办？答：检索决定召回率，Java决定返回结果是否满足硬约束。没召回就明确空，不拿其他热销充数。本地关闭向量仍保留关键词路径，但不宣称语义召回等效。

问：你报的100%是整个系统准确率吗？答：不是，是30条预标注合成需求的指定字段匹配率；不包含真实商品硬约束满足率和网络MCP成功率，两项还没有端到端实测。
