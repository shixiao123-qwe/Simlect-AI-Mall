## 1. 商品搜索和详情

入口：`Simlect-front/Simlect-web/src/api/modules.ts` 的 productApi.search。

执行链：POST `/api/search/products` → Gateway `Simlect-backend/Simlect-gateway/src/main/resources/application.yml` 的 search 路由与 RewritePath → `Simlect-backend/Simlect-search/src/main/java/com/simlect/controller/SearchController.java#searchProducts` → `component/EsSearchComponent.java#searchProducts` → ElasticsearchOperations.search → PaginationResultVO → ResponseVO → Vue搜索页面。

Controller 拒绝空关键词、反向/负价格区间、不允许的排序字段和超出结果窗口的页码。组件把 composite/price/sale映射为_score/minPrice/totalSale，组装分页查询。中文名称使用productName分词匹配，或productName.keyword子串匹配。价格为商品minPrice/maxPrice与用户区间相交，不是SKU精确可售判断。

索引同步：`Simlect-search/src/main/java/com/simlect/controller/internal/SearchToolInternalController.java#productData` → ProductFeignSupport.listOnSaleProductIds → EsSearchComponent.saveIndex → ProductFeignSupport.getSearchIndex → Product内部接口读商品 → 写/删ES。源码保存时只索引上架商品，但索引仍可能有短暂延迟；下单不信任索引价格。

详情：`Simlect-product/app/src/main/java/com/simlect/controller/ProductController.java#getProduct` → `biz/impl/ProductInfoServiceImpl.java#getProduct4VOByProductId` → ProductBloomFilterComponent.mightExist → ProductInfoMapper.selectByProductId → ProductPropertyValueMapper.selectList → ProductSkuMapper.selectList → StockFeignSupport.getAvailable → Product4VO。

布隆过滤器的角色是挡掉明显不存在的ID，不是权威数据源。`component/ProductBloomFilterComponent.java#warmUpAllProductsOnStartup` 在ApplicationReadyEvent加载商品ID；SQL直导绕过应用新增逻辑，必须重新预热。当前演示曾出现列表有商品但详情报参数错误，原因正是启动时预热0条后直接导入SQL。不能简单清空Redis或关闭全部校验掩盖问题。

面试说法：“搜索用ES提高检索能力，详情和交易仍回业务服务。召回结果、商品存在、可售SKU是不同层次。”

## 2. AI导购

`Simlect-agent/app/api/routes/agent.py` → `services/agent_service.py` → `graph/runner.py#run_agent_graph` → `graph/builder.py` → `graph/nodes.py#build_context_node/agent_loop_node` → `services/shopping_turn.py#shopping_turn`。

shopping_turn读取session_memory_service里的shoppingRequirement；调用shopping_parser.parse_shopping，把本轮条件与上一轮做Patch合并；调用mcp_tool_router.invoke(RECOMMEND_PRODUCTS) → mcp_streamable_client.call_tool → `app/mcp_server/server.py#recommend_products` → shopping_service.recommend。

推荐内部：关键词/向量并行召回 → rrf_merge合并候选ID → JavaInternalClient.post_json `/internal/product/ai/filter` → ProductInternalController.aiFilter → AiProductFilterService.filter → ProductInternalService.snapshotBatch（三类批量查询）+ StockFeignSupport.readBatch → StockInternalController.readBatch → SkuStockService.readBatch → SkuStockMapper.selectByProductIds。

Java按上架、真实SKU价格、SKU属性证据、库存筛选后，Python只对合格SKU做偏好排序并生成可追溯理由。图的shopping_handled分支在agent_runtime.finalize_agent_response中禁止原普通搜索热销补卡，再推WebSocket和持久化回复。

异常：模型输出不合法不写回新条件，明确降级普通搜索且告知预算未核验；Java/库存失败时不能返回“保证满足条件”的商品；缺品类时询问品类。原始普通搜索仍保留。更多字段规则见08。

## 3. 购物车：谁能修改哪一行

源码：`Simlect-cart/app/src/main/java/com/simlect/controller/ProductCartController.java`、`biz/impl/ProductCartServiceImpl.java`、`mappers/ProductCartMapper.java` 与 `app/src/main/resources/com/simlect/mappers/ProductCartMapper.xml`。

加入：add2Cart → 从TokenUserInfoDTO取userId覆盖请求对象 → ProductCartServiceImpl.add2Cart → 校验/处理商品与规格 → ProductCartMapper写购物车。客户端不能通过传另一个userId替别人加购。

展示：loadProductCart → 查询条件绑定当前userId → findListByPageAndUserId → 批量Product快照 → 按商品ID+属性组合映射SKU → 读取当前库存 → ProductCartVO。price代表当前SKU价，addPrice是加入时的价格参考，两者不能混为结算价格。

删除：deleteCart → ProductCartQuery同时设置cartId和userId → deleteByParam。只检查“用户已登录”不够，还必须在数据查询里绑定所属用户。

审查注意：当前findListByPageAndUserId在findListByPage后又findListByParam，存在重复列表查询；库存填充仍逐SKU请求。此次不把它写成已经优化完成。新增导购路径已批量读取，购物车可在后续性能专项中沿用，但要补业务回归。

## 4. 普通下单与库存

入口：`Simlect-order/app/src/main/java/com/simlect/controller/OrderController.java#postOrder`，调用 `biz/impl/OrderInfoServiceImpl.java#postOrder`，有本地事务及@GlobalTransactional。

按源码主要顺序理解：

1. 从登录身份和PostOrderDTO确定本次购买来源、商品项及地址等；商品/规格信息经ProductFeignSupport.snapshotBatch取得。
2. 根据真实SKU计算订单金额，而不是使用前端传入商品单价。普通券分支会调用CouponFeignSupport.validateAndLock，并分摊优惠。
3. StockFeignSupport.lockAndVerify做库存校验；将order_info、order_item、物流信息写入本地库。
4. 以`order-create-deduct:`加统一支付单号构造稳定operationId，调用changeStockBatchIdempotent扣减；来自购物车的请求再通过Cart契约删除所购项。
5. PayFeignSupport.getPayUrl构造支付信息，createPending登记待支付交易。
6. 每个订单通过TransactionalMqSender.sendAfterCommit安排支付超时消息。
7. 若后续步骤抛RuntimeException，对已尝试/已完成扣库存执行独立补偿operationId回补，解锁券；补偿失败写RemoteCompensateRecorder，不能仅打印日志就当作成功。

关键点：`StockFeignSupport.lockAndVerify`的远程调用本身不能在未启用Seata时保证锁一直跨到后续另一次RPC。最终防超卖还要看Stock事务和Mapper的条件更新；不能仅凭方法名“lock”说锁覆盖了所有分布式步骤。

`Simlect-stock/app/src/main/resources/com/simlect/mappers/SkuStockMapper.xml`：selectByKeyForUpdate用FOR UPDATE；changeStock的UPDATE含stock + changeAmount >= 0；stock_change_operation表以operation_id主键记录执行结果和取消墓碑。

本地启动器关闭Seata，演示应讲本地事务、远程幂等和补偿，不能声称验证了生产分布式事务原子性。

## 5. 支付与回调

`Simlect-pay/app/src/main/java/com/simlect/biz/PayInternalService.java` 作为内部支付门面；渠道实现 `biz/impl/PayChannel4AliPay.java#getPayUrl/payNotify/queryOrder/refund/closeOrder`。源码已有localMockEnabled路径，当前凭据/开关以本地配置为准，不能把模拟当作实际支付宝交易。

异步通知：支付宝 → `/api/notify/alipayNotify` → Gateway → `controller/PayNotifyController.java#alipayNotify` → PayChannel.payNotify验签/解析 → Redisson以支付单号加回调互斥锁 → OrderFeignSupport.paySuccess → OrderInfoServiceImpl.paySuccess → 更新订单与支付记录。

正常返回success，验签/业务处理失败返回failure。锁处理的是同一时刻的并发；重复通知隔一段时间再次到来，还要靠订单状态和稳定业务ID幂等。支付金额不是“签名正确就永远正确”，应结合订单侧金额校验分支阅读并测试。

反例：“回调URL不公开就安全”不成立；渠道回调必须匿名可达但请求真实性必须验签。浏览器支付跳转成功也不等于服务端已经收到成功通知。

## 6. 超时关单与恢复库存

`OrderInfoServiceImpl.postOrder` → `Simlect-common/src/main/java/com/simlect/constants/TransactionalMqSender.java#sendAfterCommit` → 有事务时OutboxMessageService.savePending → afterCommit.tryDispatch → RabbitMQ PAY_TIMEOUT_DELAY_KEY → TTL过期转死信 → `Simlect-order/app/src/main/java/com/simlect/component/RabbitMQPayOrderDeadListenerComponent.java#handlePayTimeoutOrder` → OrderInfoServiceImpl.cancelUnpaidOrderForPayTimeout → cancelOrder。

cancelUnpaidOrderForPayTimeout先读取订单，已经不是WAIT_PAYMENT则跳过；再检查同一payOrderId关联订单是否已有支付进展；生命周期锁忙返回false供消费侧重试。cancelOrder路径关闭支付记录、回补库存，使用稳定operationId防重复加库存。

消费侧使用MqListenerHelper进行消费幂等和有限重试。不要讲成“RabbitMQ保证消息只到一次”。OutboxDispatchTask需要`mq.outbox.dispatch-enabled`及`app.common-scheduling.enabled`两个条件，存在代码不等于每个环境都启用了补投。

方案权衡：TTL+死信无需增加新基础设施，但需要理解队列过期行为、重试、死信最终处理和延迟并非精确定时。此次没有改用Kafka或重写调度系统。

## 7. 退款与AI确认

AI只生成提案：MCP PROPOSE_REFUND → `Simlect-agent/app/services/pending_action_service.py#create` → Redis存待确认内容 → `Simlect-front/Simlect-web/src/components/agent/AgentConfirmCard.vue` → 用户confirmAction → PendingActionService.confirm → ActionExecuteService.execute → JavaBridge.refund_order，使用用户token请求Java用户接口。

PendingActionService先校验userId归属、加锁、Lua CAS从PENDING转CONFIRMED。业务明确拒绝可尝试回滚状态；系统异常可能已经执行，保持CONFIRMED防二次操作，不武断自动重发。

Java退款：`OrderController`的退款入口 → `OrderInfoServiceImpl.refund` → 校验订单属于当前用户 → 支付单生命周期锁 → refundInLock重新查状态 → 允许已付款/已发货/部分退款等状态 → Redis订单项幂等闸 → doRefund → PayFeignSupport.refund → PayChannel4AliPay.refund。

Order侧保留稳定退款单号；Pay侧`mall:pay:refund:req:` Redis闸与支付宝out_request_no相配合。远程退款成功后本地事务失败，必须使用相同退款请求号重试，不能随手生成新编号。退款库存恢复有事务同步与补偿分支，不能简单放在任何finally里“无论成功失败都加库存”。
